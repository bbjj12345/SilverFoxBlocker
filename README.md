# SilverFoxBlocker

Chrome / Edge 浏览器扩展（Manifest V3，当前版本 **v1.13.8**），用于检测并拦截「银狐木马（Silver Fox / 游蛇）」相关的钓鱼站、仿冒官网和恶意下载入口。

**检测、评分、名单比对与拦截全部在本地完成**，不依赖在线服务即可工作。默认开启的 RDAP / ICP 辅助核验会发送**域名**；云端黑 / 白名单、威胁情报 API、社区黑名单都是**需要你主动开启或点击**的增强项。当前版本包含 37 维加权检测引擎、六类名单（云端 / 内置 / 自定义 × 黑白）与三层“例外”放行层、下载与自动下载拦截、云端名单手动同步（Worker 侧 GitHub 优先、Gitee 回落）、可选四家威胁情报与五份社区黑名单、六款急救工具下载引导（含自制 SilverFoxCleaner），界面明暗四档（黑暗 / 明亮 / 跟随系统 / 反转系统），以及 GitHub / Gitee / 蓝奏云三个更新入口。

**无需账号、无遥测、无广告**：不收集浏览历史，不注入参数，不加载任何远程代码。

> 💡 **算法致敬**：检测引擎基于 [@Lolitide](https://github.com/Lolitide) 的开源作品
> [VirusDetector](https://github.com/Lolitide/VirusDetector)（MIT License）的规则算法，

### 一、本地检测与拦截（默认全部开启）

- **实时网页分析**：解析 DOM 结构、下载入口、话术特征，而不是只比对域名黑名单。
- **判定顺序（先名单、后联网）**：先查六类名单（云端 / 扩展内置 / 自定义，各有黑、白两份）与三层“例外”（云端 / 内置 / 自定义，可推翻对应层级的黑名单），命中即按名单处理，均为本地查表、毫秒级，不发起任何外部请求；未命中才**并行**查询 ICP 备案与域名年龄，并保证**页面加载完成后 5 秒内**给出结论（超时即以现有信息判定，ICP / 年龄仅作加分项）。
- **名单优先级（宁可杀错，不可放过）**：**任意黑名单 > 任意白名单**；同色内部按 **云端 > 扩展内置 > 自定义** 归因。即同一域名只要出现在任一黑名单里就判危并拦截，即使同时出现在白名单里也不豁免——避免远端可变的云端白名单被误加或投毒后开出一条绕过样本 IOC 的通道。该顺序在页面判定、评分引擎、下载拦截三条链路上完全一致。
- **三层「例外」（2026-11-23）**：白名单只能「在没有任何黑名单命中时」生效，压不住误报；例外则是**能主动推翻黑名单**的放行层，判定顺序为 **云端例外 > 云端黑名单 > 扩展内置例外 > 扩展内置黑名单 > 自定义例外 > 自定义黑名单 > 三档白名单**。三层各管一件事：**云端例外**由作者随云端名单下发，用来热修「云端通配误伤知名企业官网」这类大面积误报（不必等发版）；**内置例外**写死在 `rules/iocs.js` 的 `EXCEPTION_DOMAINS`，处理内置黑名单的已知冲突；**自定义例外**在「规则与名单 → 自定义恶意域名黑名单」页里由用户自己填，用来拯救被自己写错的黑名单误伤的站点。刻意**不**让用户例外推翻云端/内置黑名单——否则钓鱼站只要诱导用户点一次「信任」就能突破整条防线。例外同样支持精确 / 后缀 / 通配 /（云端例外还支持）路径，但不允许通配顶级域：它是放行侧，一条写宽的例外等于给半个互联网开免检通道。三种途径的具体写法、操作步骤与排查方法见下文《🩹 如何添加例外》。
- **名单粒度（域名 / 链接两级）**：云端黑、白名单都支持纯主机名（`example.com`，覆盖该域名及其全部子域）与「主机名/路径」（`wwavz.lanzout.com/b01gigjayb`）两种写法，后者只对匹配的链接及其子路径生效（前缀须落在 `/` 边界，`/b01gigjayb2` 不命中；只比对 pathname，忽略查询串与锚点）。路径条目在**页面判定与下载拦截**两条链路上同时生效，适合「只信任某个网盘分享链接、同站其它页面照常检测」的场景。
- **多维加权评分**：官方域名早期退出、ICP 备案核验、域名仿冒检测（编辑距离 / 去连字符比对）、代码工程化与 AI 生成痕迹评估、诱导下载链路（占位按钮 / 脚本集中下载地址 / 多平台共用安装包 / 运行时改写）等 37 个可独立开关的检测维度。
- **域名仿冒：两条独立判定线（v1.13.6）**：判定顺序为「例外域名 / 官方域 / UGC 托管免判 → 品牌方自有域名豁免 → 权威备案跳过 → **basic**（段精确匹配、子串包含、编辑距离 typo、去连字符；最准，60 分；段精确匹配对「通用行业缩写 + 裸域」不计分，见下一条）→ **变体分支**（同一批品牌词另算字母多重集：纯重排、品牌词 + 2~3 个非构词词缀的字母、被连字符拆开的品牌词拼接后一致；45 分）→ **子串包含**（品牌词整段嵌在更长的标签里、前后只是填充片段；30 分）」。三级是**取最高并短路**的关系：basic 命中就不再跑后两级，一页只会出现一条「域名仿冒」理由，从结构上排除「两条线各加一次分」的双计。后两级一律标记为 soft，**不参与**「强特征组合升级」，所以单条近似拼写不会直接把页面判死（`webchat.com`、`deepseeker.com` 这类英文词撞车因此仍是 0 分）。两条线共用**同一道豁免闸门**（例外域名 / 官方域 / 内置白名单通配 / UGC 托管）与**同一份英文词排除表**，改一处两边同时生效；变体分支**不是独立维度**，跟随「域名仿冒」这一个开关，控制面板里没有单独入口。
- **数字形近（v1.13.6）**：把数字当成「一个字符的多种读法」而不是固定置换 —— `1` 既可以是 `l`、也可以是 `i`，`5`→`s`、`3`→`e`、`4`→`a`、`0`→`o`、`7`→`t`、`2`→`z`、`6`/`9`→`g`、`8`→`b`。判据很紧：**与品牌词等长 + 非数字位置逐字相同 + 数字顶替 1~2 处**，命中按 typo 计 60 分。修的是 `ba1du.com` 这类漏报：旧逻辑只把 `1` 折成 `l`，得到 `baldu`，与 `baidu` 首尾都咬不住（LCP/LCS 均 2），typo 的 `max(lcp,lcs) ≥ 4` 与变体分支的 `lcp ≥ 3` 双双失效，结果为 0 分；现在 `ba1du` / `b41du` / `al1pay` / `x1aomi` / `app1e` 均判危。反向不认：`hao123` / `51job` / `12306` 这类自带数字的品牌或普通域名不受影响（品牌词自己的数字位不参与替换）。它与 typo 同属「拼写对不上」，「访问正确的页面」照旧能反查官网（`ba1du.com` 会直接给出 `baidu.com`）。
- **本轮顺带修掉的四个既有问题（v1.13.6）**：① `normalizeHomoglyph` 会把 `deepseek10` 折成 `deepseeklo`、`deepseek2026` 折成 `deepseek2o26`，原本「品牌词 + 数字」的子串判定在剥掉数字后只剩 `lo` / `2o26` 这种**假剩余**，整条规则失效（只剩变体分支的 45 分）—— 改为**原始标签与形近折叠标签各扫一遍**（两组相同时只扫一遍，不做双倍开销），`deepseek10` 回到 60 分；② 剥首尾词缀的判断用了严格 `>`，`deepseekcn` / `deepseekapp` / `deepseekvip` 剥完与品牌词等长却被判「没有变化」而停在 45 分，改成 `>=` 后回到 60 分；③ typo 分支的两条结构护栏（`lcp ≥ 2`、`d=2` 要求两端咬合）实测把 900 个单字符变异样本漏掉 205 条（23%，含 `eepseek` / `aipay` / `penai` / `wchatpay`），**全部撤回**，改用「常用英文词排除表」治理 `discard.com` / `webchat.com` 这类真英文词误报：词表由 `tools/test-brand-variant.js` 拿 9424 个 google-10000-english 词离线扫描生成，只收**实测撞上**的词（当前 69 个），跑完 0 误报；④ 窗口拼接把 `my-deep-seek-app` 这类「品牌词 + 站点性质词」判成 45 分，改为按「品牌词之外还剩什么」分档 —— 只剩 `my` / `the` / `app` / `tool` / `open` / `fan` 这类词时降为 **30 分**（单独够不到可疑线 42），有实义词（`cnds-deep-seek-harness`）仍是 45 分。
- **ICP 权威核验：从「阻塞换源」改成「对冲 + 迟到重判」（v1.13.6）**：「盗用他人备案号」55 分必须同时满足「权威库查询成功 + 本域名无记录 + 页面展示了备案号」，**任何一次查询失败都等于这条规则静默失效**——这正是 `ai.deekseep-e.com.cn` 长期只有 45 分（仅变体分）的原因。实测两个公共接口的真实行为（本机多轮）：① `uapis` **有备案** 70~200ms 就回 `200 + serviceLicence`，**无备案**却要 **8~10 秒**才回 `HTTP 404 {"code":"NOT_FOUND"}`；② `apihz` 两个方向都在 0.9~2.8s 内回，但公开 demo key 限 10 次/分钟，超限返回 `code:400 + "调用频次过快"`；③ 同一域名两次请求，`apihz` 的「无记录」会出现**两种形状**——`code:400 + msg:"查询失败或没有备案。"` 与 `code:200 + type/icp 全为"查询失败"`，旧解析只认前者。上一版把单源超时压到 1.5s 想让第二源拿到预算，结果适得其反：8~10s 才到的那个 404 必然被掐断，「接受 404 = 无记录」那段逻辑成了**不可达代码**，于是永远 `queried:false`。现在的分工是：`uapis` 立刻发（有备案时 200ms 内定案）；`apihz` **延迟 400ms 对冲**，只有 `uapis` 没在 400ms 内给出确定结论时才真正发请求（既有备案的正常站不会把域名多披露给第二个接口，也省它的令牌）；谁先给出**确定结论**（确有备案 / 明确无记录）谁胜出，立刻 abort 另一个；单源上限 9s、总预算 10s，让那 8~10s 的 404 也能在预算内到达。同时把 `apihz` 的第二种「全字段查询失败」形状收进解析（限流文案仍排除在外，绝不把「查不到原因」当成「权威确认无备案」）。**内容脚本不再为 ICP 阻塞判定**：判定照旧在 5s 预算内出结论，权威结论若迟到则**再重判一次**——但只允许「变严」这一种（页面展示了备案号 + 权威库确认无记录 → 补上 55 分「盗用」），反向（迟到确认确有备案 → 少扣 18 分）故意不重判，避免「先报危、后变安全」的判定抖动；重判只发生一次，且带 SPA 代数校验（换路由即丢弃）。实测（真实网络 + `vm` 载入真实 `background.js`）：`ai.deekseep-e.com.cn` 4.9s 拿到 `{queried:true, hasIcp:false}`（来源 `apihz`），补强后判定 **100 分判危**（变体 45 + 盗用 55）；`baidu.com` 192ms 由 `uapis` 单源定案（对冲未触发）。回归用例见 `tools/test-icp-query.js`（15 条：404 口径、参数错误、限流、两种无记录形状、对冲不惊动第二源、慢 404 不被掐断、缓存）。

- **拦截任意下载入口**：`<a>` / `<button>` / `<div>` 等任意元素；同时覆盖 JS 程序化下载（`window.open` / `a.click` / `blob` / `location` 跳转）。
- **自动下载竞速兜底**：`<meta refresh>`、服务端强制下载（`Content-Disposition: attachment`）等「自动下载」场景也能拦截。
- **分析期下载入口置灰**：判定尚未出结论时，页面上识别得出的下载入口统一降透明度 + 去饱和（`cursor: not-allowed`），只改视觉、不摘 `href`、不禁用事件——真正的边界仍是点击拦截与后台闸门；判定一结束立刻原样恢复。
- **「无手势」自动下载拦截（增强）**：扩展自己维护一份「用户手势」时序（内容脚本在真实点击 / 回车时上报时间戳，只认 `isTrusted`，页面脚本合成的 `a.click()` 不算）。高危文件在**没有对应手势**时一律先暂停：分析期内 1.5 秒、分析结束后 4 秒的窗口；分「强手势」（点在链接 / 按钮 / `[download]` 上）与「弱手势」（滚页面、点空白、别的标签页操作），只有强手势能作为放行依据。
- **下载授权模型（每页 + 每站首次）**：本页确认过一次后，本页后续下载不再逐条询问（刷新 / 跳转即撤销）；新标签页若与父页同站，会继承父页授权。此外**每个站点第一次**下载可执行文件时必须再确认一次——这条优先于所有「用户意图」判定，因为流氓站正是用假的「下载」按钮骗取那一次点击。记录只存本机（`storage.local`），180 天后过期，点「保持拦截」不会写入。
- **下载闸门：暂停 / 继续，而不是取消 / 重下（v1.13.8）**：命中闸门时用 `chrome.downloads.pause()` 挂住**同一条**下载，用户点「继续下载」时用 `resume()` 让它接着跑；不再像旧实现那样 `cancel` + `erase` 之后再 `chrome.downloads.download({url})` 重新发一次请求。改的原因（实测三条）：① 重发出来的是「扩展发起的下载」，页面上没有 `mousedown → mouseup → click` 这条事件链，IDM / 迅雷 / Rayburst 这类把点击链上报给原生进程的下载器完全收不到信号，结果浏览器自己下完、下载器毫无反应；② 重发丢掉了原请求的 `Referer` 与 `Cookie`，需要站内鉴权的直链会 403；③ 取消发生在响应头解析前后，`Content-Disposition` 里的文件名拿不到，重下只能退化成 URL 末段——表现就是「下到一个乱码文件，手动补 `.zip` 后缀才正常」。现在下载栏里看到的是「已暂停」，判定安全后自动续传同一条，判定危险才真正取消并擦除。
- **与第三方下载器的协作（v1.13.8，逐个实测）**：本机核对了 IDM 6.43.18、NeatDownloadManager、Free Download Manager、AB Download Manager、Gopeed、Motrix、BitComet、迅雷、Ghost Downloader、Rayburst Connect 以及三个 qBittorrent 扩展的接管路径。结论是**普通下载两边互不干扰**（它们各自走原生通道与 `downloads` 事件，本扩展只读不抢）；只有「本扩展主动暂停的那一条」可能被下载器抢先 `cancel + erase` 接走——这种情况下扩展**不再弹确认条**，只提示「该下载已被 IDM / 迅雷 等下载器接管」，避免用户点「继续下载」后与下载器里那份撞成重复下载；「继续下载」时也会先确认同 URL 是否已有在跑的下载，有就不再重放。
- **放行轻提示**：判定为「用户意图」而放行时（非「本页已授权」），左下角显示一条青色提示：「已按你的点击放行下载」+ 文件名与站点，10 秒自动关闭、可点「知道了」提前关；只告知不拦截，若其实是误判可直接去下载列表取消。
- **下载器接管提示（静态）**：拦截 / 询问下载时附带一行「若你装了 IDM / 迅雷，它可能在点击瞬间就接管了链接」的说明（设置页可关）。这是**条件式提示而非检测结果**——扩展无法枚举其它扩展或原生进程，因此不会出现「已检测到 IDM」这种假判断。
- **跳转链污染追踪**：危险站跳转到新域名后，仍能识别并拦截下游下载。
- **下载发现层**：递归解析内联脚本里的直链、`.txt` 里藏的真实地址、meta refresh 目标、iframe 嵌套资源，弥补「只有指定 URL 才拦得住」的短板。
- **解析器跟随（「运行时取链」，2026-11-20）**：对**已判危且下载入口已被禁用**的页面，用一个**不激活的后台标签页**重跑它自己的「同源跳转端点」（`/go/`、`download.php?id=…` 这类把真载荷藏在 302 里的地址），把最终落点的载荷域写进本机自动学习黑名单。每页最多 2 个、5 秒超时、同一地址 1 分钟去重；只读请求 URL，不阻断也不改写（`webRequest` 的非阻塞用法），不新增任何第三方请求。可在「设置 → 拦截行为 → 运行时取链探测」关闭（默认开）。
- **载荷地址静态嗅探（2026-11-24）**：危险页的「下载」按钮常常**直接**指向第三方对象存储上的安装包（例：`https://qqqqwwee8899.tos-cn-beijing.volces.com/124322281030_setup.zip` 写在 `<a href>` 里，hover 就能看到），但因为没人点，`downloads.onCreated` 从不触发，「自动学习」也就学不到。现在页面判危后会**静态**扫一遍 DOM（被禁用的入口原地址 `data-sf-original-href`、全部 `href` / `data-*`、内联 `<script>` 里的绝对 URL、`meta refresh`），只收载荷扩展名与 `/download`、`/dsluc` 这类分发页地址；**只读页面、不发请求**。共享对象存储（火山 TOS / 阿里 OSS / 腾讯 COS / 七牛 / 又拍…）只记到**桶级**（`桶.区域.平台`），绝不已平台注册域记账 —— 否则会把整个对象存储（含大量正常文件）一起拦掉。
- **智能免误拦**：官方 / 搜索引擎 / 可信分发（GitHub、网盘等）白名单；`file://`、浏览器内部页、localhost 自动跳过。

### 二、作者维护的云端黑 / 白名单（手动同步，默认无数据）

- **数据来源**：作者维护的 `whitelist.json` / `blacklist.json`（托管在作者的私有 GitHub 仓库，作者侧另有 Gitee 私有镜像仓库作为 GitHub 不可达时的服务端备源），经自建 Cloudflare Worker 的 `GET /list?type=white|black` 实时读取并转发。请求只带一个随扩展分发的只读 `X-API-Key`（用于 Worker 对扩展鉴权，不是你的身份标识），**不上传任何本地数据**。响应头 `X-Data-Source` 会注明这次数据取自 `GitHub` 还是 `Gitee`，设置页状态行显示为「数据源：云端接口·Gitee」。此外 Worker 每天对名单里的**正常网址**做一次存活巡检（结果在 `GET /health`，不回传给扩展；通配条目跳过）：先用带桌面浏览器 UA 的 GET 直接访问一次，**拿到任何 HTTP 响应（含 403/404/500）就算活着**；只有「连不上且 DNS 里查不到」或「连不上且注册局明确无记录 / 已注销」才记为疑似失效，其余「打不开但域名还在」的条目单列出来、**不自动删除**。注意巡检**会真的访问被拉黑站点**，Cloudflare 的出口 IP 会暴露给对方——这是判断「浏览器能不能打开」绕不开的代价（只问 RDAP 的旧做法不碰站点，但也答不了这个问题）。单次最多探 **25 条**，名单更长时按游标顺序往后探、走到名单尾部再回到开头（同一轮不会重复探刚探过的条目），分几天覆盖一轮；同时按**实际子请求数**（30 次）兜底截断，并在每批启动前预留「单条最坏耗时」（约 18 秒），确保整轮不超过 30 秒墙钟——免费版每个请求上限 50 次子请求，按条数估算会在「一堆死站、每条都要走 https+http+DoH+RDAP」时整轮失败，所以宁可少探几条、剩下的留到下一轮。巡检跑完会把结果**发一封邮件**到 `feedback@silverfoxblocker.dpdns.org`，再由 Cloudflare Email Routing 转发给作者：**私人邮箱地址不在代码和仓库里**，换邮箱只改面板里的路由规则；没配 `BREVO_API_KEY` 时自动跳过发信，巡检本身照常完成。

## 🛡️ 工作原理

1. **采集**：页面域名、HTML、下载链接、代码特征。
2. **名单短路**：六类名单本地查表，命中黑名单直接判危、命中白名单跳过评分；例外（云端 / 内置 / 自定义）按优先级推翻对应层级的黑名单；未命中才进入评分。
3. **评分**：加权评分引擎得出 0–200+ 风险分，并行查询 RDAP / ICP 作为加分项，命中组合信号直接升级为危险。
4. **预警**：跨过阈值触发 `warn`（顶部提示）或 `danger`（拦截浮层 + 禁用下载入口）。
5. **兜底**：后台 `chrome.downloads` 监听，覆盖内容脚本判定前的自动下载。
6. **可选增强**：威胁情报 API 与社区黑名单命中后追加情报横幅；云端名单快照由你手动同步。

## 🩹 如何添加例外（放行被误拦的站点）

**先分清「白名单」和「例外」**：白名单只是让一个站点**免于评分**，一旦这个域名出现在任何黑名单里，白名单照样不生效；例外才是**能推翻黑名单**的放行层。所以要救一个「被名单拉黑」的站点（尤其是被自己填错的黑名单误伤），要写**例外**，写白名单没用。

### 三条例外，各管一层

| 途径 | 在哪里写 | 能推翻什么 | 适合什么场景 |
|---|---|---|---|
| **自定义例外**（你自己就能改） | 设置 →「规则与名单」→「自定义恶意域名黑名单」下方的**「自定义黑名单例外」**文本框，一行一个域名 | 只推翻**自定义黑名单** | 手滑把官网填进了自己的黑名单 |
| **扩展内置例外**（随扩展发版） | `rules/iocs.js` 里的 `EXCEPTION_DOMAINS` 数组 | 推翻**扩展内置黑名单** | 内置名单与真实官网冲突，随版本修正 |
| **云端例外**（作者下发，优先级最高） | 云端 `whitelist.json` 的 `exceptions` 数组，随云端名单同步到本地 | 推翻**云端黑名单** | 云端通配误伤一堆官网，需要热修、不必等发版 |

判定顺序是固定的一条链，命中即停：

```
云端例外 → 云端黑名单 → 扩展内置例外 → 扩展内置黑名单
        → 自定义例外 → 自定义黑名单 → 云端白名单 → 内置白名单 → 自定义白名单
```

刻意**不让**自定义例外推翻云端 / 内置黑名单：否则钓鱼站只要骗你点一次「信任」，就能绕过整条防线。

### 最常用的一条：加自定义例外

1. 打开设置页：点工具栏图标 → 齿轮（或在 `chrome://extensions` 里点本扩展的「扩展程序选项」）。
2. 切到「规则与名单」，找到「自定义恶意域名黑名单」卡片下方的**「自定义黑名单例外」**。
3. 一行写一个域名。只放行某个子域就写 `bbs.example.com`；连同所有子域放行写 `*.example.com`（等价于 `example.com`）。
4. 点页面底部的**「保存设置」**（这个页面不会自动保存），然后**刷新那个网站**——已经打开的页面不会自己改结论。
5. 回到该站，工具栏弹窗应显示「已跳过评分」，原因一栏写着「自定义例外：该域名在自定义例外名单中……」，说明例外生效了。

写法与白名单完全一致：精确主机名、子域后缀、`*` / `?` 同级通配（`*` 不跨 `.`），**不支持顶级域通配**（`*.com`、`foo.*` 会被丢弃），条数不限。导出的配置 JSON 里字段名是 `exceptionDomains`，导入别人的配置时会一并带进来。

### 例外不生效时按这个顺序排查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 写了自定义例外，站点还是被拦 | 它命中的是**云端或内置**黑名单，自定义例外压不住 | 用「反馈与建议」报误报；作者可下发云端例外热修，或改内置表随版本修正 |
| 站点不在任何黑名单里，却仍被判危 | 是**评分引擎**判的（仿冒域名、缺 ICP、话术特征、下载行为等），例外只管名单 | 改用「自定义信任域名白名单」；确信是误判请反馈 |
| 写了条目但看起来没收录 | 写法被护栏丢弃（TLD 通配、`*.*`、`foo.*` 这类） | 在「关于 → 未生效条目」看原因码，改成具体域名 |
| 云端名单更新后例外没反应 | 云端名单**不会自动同步** | 「关于 → 从云端更新名单」，成功后再刷新页面 |

### 维护者：云端例外与内置例外怎么写

云端 `whitelist.json` 在 `domains` / `correct_sites` 同级加 `exceptions`，纯字符串数组，写法与云端黑名单一致（精确 / 后缀 / 通配 / `主机名/路径` 都支持）：

```json
{
  "domains": [ "..." ],
  "correct_sites": [ "..." ],
  "exceptions": [ "example.com", "*.example.com", "pan.example.com/s/abc123" ]
}
```

路径条目只对该链接及其子路径生效（前缀须落在 `/` 边界），适合「只放行某个网盘分享页、同站其它页面照常检测」。改完用 `node tools/encrypt_cloud.js` 重新生成 `Cloud/*.json.enc`（建议加 `--verify` 复核），扩展侧点一次「从云端更新名单」即生效，**不需要发版**。

内置例外则直接改 `rules/iocs.js` 的 `EXCEPTION_DOMAINS`（当前是空数组，作为「内置黑名单与真实官网冲突」的兜底位保留），改完跑 `node tools/test-exception.js` 核对优先级矩阵与通配护栏。

## 🔑 权限说明

`manifest.json` 只申请 **7 项 API 权限 + 1 项主机权限**，每一条都对应一个你能直接看到的动作，没有「先申请着、以后可能用」的权限。

| 权限 | 具体用在哪 | 申请理由 | 不授予的后果 | 外发数据 |
|---|---|---|---|---|
| `storage` | `storage.sync` 存设置 / 权重 / 自定义名单 / 三个 API Key（VirusTotal / GSB / FoxAPI，AES-GCM 密文）；`storage.local` 存统计、云端名单快照、社区名单、下载黑名单；`storage.session` 存本会话的危险标签页 | MV3 的 Service Worker 空闲 30 秒即被回收，设置与状态只能放 storage；不存就无法「记住你调过的每一个开关」 | 每次重启恢复默认，名单与统计全丢 | 否（除非你开了浏览器账号同步，那是浏览器厂商的行为） |
| `unlimitedStorage` | 云端名单镜像、社区名单（PhishDestroy 域名表、HaGeZi 布隆位图、uBlock / Dandelion 的小位图）、自定义背景 | 这些体积超过扩展默认配额；超限时 `storage.local.set` 会**静默失败**，表现成「提示同步成功、名单却没变」 | 开启社区名单后可能写盘失败 | 否 |
| `downloads` | ① 命中黑名单 / 载荷特征时 `chrome.downloads.cancel` 真正阻断下载；② 命中分析闸门或「每站首次确认」时用 `pause` / `resume` **暂停并续传同一条**下载（v1.13.8 起不再取消后重下）；③ 「银狐急救」里你点工具时发起下载并指定文件名 | 只靠页面提示拦不住已经开始的下载；急救工具也需要一个可信的下载入口 | 只能弹提示，高危文件照样落地 | 否（只从官方域名下载，且必须你点击） |

### 后端链路（由 Worker 发起，不是扩展）

`GET /list` 由 Worker 先向 `api.github.com` 读取私有仓库里的 `whitelist.json` / `blacklist.json`（依次尝试仓库根目录与 `List/` 两种布局）；GitHub 不通或令牌失效时，自动改用 `gitee.com/api/v5/.../raw/...` 读取同一份文件的 Gitee 私有镜像仓库（依次尝试 `master` / `main` / 仓库默认分支）。时间分配上主源最多占 4.5s、总预算 9s（比扩展侧云端接口 10s 超时短），保证「GitHub 卡死」时备源一定还有时间跑。两个源都读不到、或拿回来的内容不是名单（没有 `domains` 数组）时返回 502 并附逐通道的失败原因，扩展侧据此提示「名单同步失败」，不会把本地名单清空。`POST` 由 Worker 经 `api.brevo.com` 发信到 `feedback@silverfoxblocker.dpdns.org`，再经邮件路由转给作者。**只有 POST**（反馈与名单上报）会走 KV 限流：按「IP + 日期」计数，60 次/天/IP、24 小时过期；Worker 同时开启了调用日志，因此两类请求在服务端都可能留下来源 IP 记录。

> 排查用（两者都要 `X-API-Key`）：
> - `GET /list?type=black&diag=1` 只返回逐通道的尝试结果（哪个源、哪条路径、哪个分支、HTTP 状态、耗时），不返回名单正文。
> - `GET /list?type=black&force=gitee&diag=1` 跳过 GitHub，**只**走 Gitee，用来验证备源是否真的可用；`force=github` 反之。扩展同步永远不带 `force`，线上行为仍是 GitHub 优先、Gitee 兜底。

> 早期上游版本会从 `site-directory-cache.pages.dev` 拉取第三方「官方域名库」，已于 2026-11-01 移除。**当前版本的云端名单是作者自行维护的黑 / 白名单，不是第三方官方站点清单，也不含任何可执行内容。**

## ⚠️ 可能误拦与免责

本扩展采用**启发式特征评分**。虽已内置官方 / 可信分发白名单、`file://` 与浏览器内部页自动跳过等免误拦措施，但**仍可能把个别正常网站误判为风险**。

遇到误拦，先判断是**哪一类判定**在挡你（工具栏弹窗里会写依据）：

1. **命中了黑名单**（云端 / 内置 / 自定义）：白名单救不了这种情况，要加**例外**——自己填错的黑名单用「自定义黑名单例外」；云端或内置黑名单误伤，请报误报，由作者下发云端例外或随版本修正内置表。三种途径的写法与步骤见《🩹 如何添加例外》。
2. **评分引擎判危**（仿冒域名、缺备案、话术特征等）：在设置 →「规则与名单」→ 自定义信任域名白名单里加上该域名，立即放行（白名单只在这类「没被任何黑名单命中」的场合生效）。
3. 无论哪一类，都可以在「关于」页选「误报」提交反馈（GitHub Issue 或邮件）。
4. 只是临时看一眼：拦截浮层里选「继续访问（仍拦截下载）」，需二次确认。

> 它只负责「在你被诱导下载前尝试阻止」，不能替代专业的安全软件；急救工具也请自行核对来源与扫描结果后再处理。发现漏报同样欢迎反馈。

## ⚠️ 已知限制：第三方下载器（IDM / 迅雷 / Rayburst 等）

浏览器扩展**只能在 Chrome / Edge 的下载与网络栈内动手**。下载器通常装一个原生 companion 进程 + 浏览器插件，在「点击 / 右键 / mousedown」阶段就把 URL 抢走、由它自己的进程下载——此时 `chrome.downloads.onCreated` **根本不会触发**，后台兜底层失效。

**页面侧的钩子也压不住它们**（v1.13.8 逐个核对过 IDM 6.43.18、NDM、FDM、ABDM、Gopeed、Motrix、BitComet、迅雷、Ghost Downloader、Rayburst Connect）：这些下载器普遍把监听挂在 `window` 的**捕获阶段**，而 DOM 事件链里 `window` 比 `document` 先到，本扩展挂在 `document` 的下载入口钩子（`mousedown` / `pointerdown` / `click`）抢不到前手；MV3 又拿不到 `webRequestBlocking`，无法在网络层取消它们的请求。所以「临时关闭下载器的浏览器接管」仍是风险页上最可靠的办法。

本扩展实际能做的有三层：

- **不让页面先拿到 URL**（`document_start` 即安装）：覆盖 `window.open`、`<a>.click` 原型、`location` 跳转，并把命中下载入口的元素置灰、移除 `href`、`pointer-events:none`、拦截 `contextmenu`；
- **在浏览器已经创建下载之后**：用 `pause` / `resume` 把它按住或放行（v1.13.8 起，见上文「下载闸门」）。暂停用的是**同一条下载**，所以下载器的接管流程与它兼容；如果下载器抢先 `cancel + erase` 接走了条目，扩展只提示「已被下载器接管」，不会硬塞一条确认条让你点；
- **警示提醒**：风险页浮层提示「临时关闭下载器的浏览器接管」；每次拦截 / 询问下载时，确认条与拦截弹窗里都会附一行静态提示「若你装了 IDM / 迅雷，它可能已接管该链接，请到下载器里检查并取消」（设置页可关）。
- **诚实边界**：这一行是**条件式提示，不是检测结果**——浏览器扩展无法枚举其它扩展或原生进程，因此不会声称「已检测到 IDM」。它的作用是消掉「扩展说拦住了、文件却在下」的困惑。

> 仍无法覆盖：手动复制 URL 粘进下载器、或把下载器设为系统默认下载器——这类下载完全不经过浏览器，任何扩展都拦不住。
